• Да — ручная экспертная разметка сейчас выглядит самым полезным следующим шагом. Главный предел качества уже не
  столько в признаках, сколько в источнике правильных меток: модель не может научиться находить срывы, которые wavelet
  teacher систематически не считает срывами.

  При этом обнаружился важный нюанс с test1:

  - sht38818 уже находится в hard и попал в обучающую часть набора. Wavelet teacher дал ему только 5 подтверждённых
    событий, а ML сейчас возвращает те же 5 событий примерно в тех же местах.

  - sht38811 находится в validation и участвовал в выборе порога модели. Teacher записал для него 27 событий.
  - Копии обоих файлов также лежат в random и test1.

  Поэтому test1 пока не является независимым тестом. Но эти разряды очень полезны для разработки экспертной разметки.

  Есть также различие между обычным запуском wavelet и обучающим teacher:

  - обычный wavelet на SXR 50 нашёл 14 событий для 38811 и 0 для 38818;
  - многоканальный teacher нашёл соответственно 27 и 5;
  - поэтому сохранённая обучающая разметка немного лучше одноканального результата, но всё равно неполна, особенно для
    38818.

  ## Что сейчас ограничивает качество

  ### 1. Пропущенные wavelet-события превращаются в отрицательные примеры

  Это наиболее опасная проблема. Если POSR предлагает настоящий срыв, которого нет в teacher-разметке, то сейчас
  возможны два исхода:

  - далеко от teacher-событий — кандидат получает метку 0;
  - близко к uncertain teacher-событию — кандидат игнорируется.

  То есть модель может прямо учиться отвергать реальные сложные срывы.

  ### 2. У детектора есть потолок полноты proposals

  Feature-ML классифицирует только события, предложенные POSR/CPD. Если истинный срыв не предложил ни один генератор,
  никакие дополнительные признаки его не восстановят.

  Нужно отдельно измерять:

  Истинный срыв
      ├── есть proposal → проблема классификатора
      └── нет proposal  → проблема генератора кандидатов

  Это можно понять только после появления ручной разметки.

  ### 3. Метрики сейчас измеряют сходство с wavelet, а не с экспертом

  Validation F1 около 0.91–0.92 означает в первую очередь, что ML неплохо воспроизводит псевдоразметку. Это ещё не
  означает такую же полноту по реальным срывам.

  Кроме того, у текущих моделей точность на train равна 1.0. При 46 обучающих разрядах это явный признак того, что
  ёмкость модели велика относительно числа независимых экспериментов.

  ### 4. Признаков действительно может быть много

  Сейчас:

  - reference_sxr — 16 признаков;
  - core_diagnostics — 154;
  - full — 218.

  При этом важно считать не тысячи кандидатов, а именно независимые разряды: сейчас их 46 в train и 10 в validation.
  Тысячи кандидатов одного разряда сильно коррелированы и не эквивалентны тысячам независимых наблюдений.

  Поэтому 218 признаков для такого числа разрядов действительно могут приводить к переобучению. Но сначала я бы
  исправила разметку: отбор признаков по ошибочным teacher-меткам может оставить именно признаки, которые лучше всего
  повторяют ошибки wavelet.

  ## Как я предлагаю вводить ручную разметку

  Не делать отдельное «дообучение» модели только на двух файлах. Текущий HistGradientBoostingClassifier не является
  инкрементальной моделью, а обучение на маленькой ручной добавке легко испортит уже выученное.

  Правильнее каждый раз переобучать модель с нуля на смешанном наборе:

  1. экспертная разметка имеет приоритет;
  2. для остальных разрядов временно остаётся wavelet-псевдоразметка;
  3. неуверенные экспертные области исключаются из обучения;
  4. полностью просмотренные области позволяют надёжно создавать отрицательные примеры;
  5. train/validation/test по-прежнему разделяются целыми разрядами.

  То есть wavelet станет не «истиной», а способом дешёво предварительно разметить ещё не просмотренные файлы.

  ## Каким должен быть JSON

  Разметку лучше задавать событиями всего разряда, а не создавать отдельную копию физического срыва для каждой толщины
  фольги.

  Пример:

  {
    "schema_version": 2,
    "shots": [
      {
        "shot_id": "sht38818",
        "relative_path": "hard/sht38818.SHT",
        "review_status": "complete",
        "shot_label": "sawtooth",
        "reviewed_intervals_s": [
          [0.1485, 0.2250]
        ],
        "events": [
          {
            "time_s": 0.17966,
            "label": "sawtooth",
            "confidence": "certain",
            "tolerance_s": 0.0003,
            "reference_sxr": "SXR 15 мкм",
            "visible_sxr": [
              "SXR 15 мкм",
              "SXR 27 мкм"
            ],
            "note": ""
          },
          {
            "time_s": 0.2038,
            "label": "uncertain",
            "confidence": "uncertain",
            "tolerance_s": 0.0005
          }
        ]
      }
    ]
  }

  Важны следующие поля:

  - time_s — абсолютное время на полной временной оси SHT;
  - reviewed_intervals_s — области, которые действительно просмотрены;
  - review_status — partial или complete;
  - uncertain — событие, которое нельзя честно отнести ни к 0, ни к 1;
  - reference_sxr — канал, на котором время проще всего поставить;
  - visible_sxr — где событие визуально заметно.

  Поле с толщиной фольги можно поддержать, но лучше хранить стандартное имя SXR-канала: из него толщина однозначно
  следует.

  Без reviewed_intervals_s отсутствие события в JSON нельзя трактовать как отрицательную метку: возможно, пользователь
  просто не разметил оставшуюся часть сигнала.

  ## Каким должен быть интерфейс

  Для регулярной работы локальный интерфейс будет значительно удобнее ручного редактирования JSON. Для этого хорошо
  подходит Streamlit или Dash с Plotly.

  В интерфейсе стоит показывать:

  - все доступные SXR 15/27/50/80/127 на общей синхронизированной оси;
  - ток плазмы;
  - при необходимости D-alpha и другие диагностические каналы;
  - wavelet teacher;
  - raw POSR;
  - raw CPD;
  - текущие ML-срабатывания и вероятности;
  - начало токового плато.

  Эксперт должен уметь:

  - нажать в любом месте графика и добавить срыв;
  - перетащить метку для уточнения времени;
  - отметить событие как certain или uncertain;
  - удалить ложную автоматическую метку;
  - отметить просмотренный временной интервал;
  - указать, что в просмотренном интервале событий больше нет;
  - сохранить и перейти к следующему разряду.

  Критически важно: нельзя ограничивать выбор только точками POSR/CPD. Иначе событие, пропущенное обоими генераторами,
  невозможно будет добавить, и мы никогда не измерим реальный recall proposals. Привязку клика к ближайшему proposal
  можно сделать опциональной.

  ## Что делать с ручным событием, для которого нет proposal

  На обучении его можно принудительно добавить как кандидата в точном экспертном времени. Это позволит извлечь признаки
  и показать модели положительный пример.

  Но это не исправит runtime автоматически: при детектировании такого экспертного времени уже не будет. Поэтому
  pipeline должен вести отдельную статистику:

  - доля экспертных событий, возле которых есть POSR proposal;
  - доля с CPD proposal;
  - доля хотя бы с одним proposal;
  - перечень событий, пропущенных всеми генераторами.

  Если таких пропусков много, следующим изменением будет генератор с повышенной полнотой: например, более мягкий POSR,
  объединение raw POSR и raw CPD либо дополнительный генератор по локальным экстремумам производной. Ложние кандидаты
  затем должен отсеивать классификатор.

  ## Как это обычно делают в больших проектах

  Обычная схема называется human-in-the-loop или active learning:

  1. автоматический алгоритм размечает простые случаи;
  2. эксперт размечает сложные и неоднозначные;
  3. система показывает в первую очередь случаи, где модель не уверена или расходится с wavelet/POSR/CPD;
  4. экспертные метки версионируются и никогда не перезаписываются автоматикой;
  5. модель полностью переобучается;
  6. качество проверяется на отдельном экспертно размеченном наборе, который не участвует ни в обучении, ни в подборе
     порога;

  7. цикл повторяется.

  Для нашего небольшого набора это особенно эффективно: не обязательно вручную просматривать все 228 разрядов. Сначала
  можно качественно разметить примерно:

  - 10–20 наиболее сложных разрядов для обучения;
  - 5–10 отдельных сложных разрядов оставить как постоянный gold-test;
  - затем добавлять разряды, на которых модель ошибается или не уверена.

  ## Предлагаемый следующий этап

  Я бы разбила его на два блока.

  Первый блок — фундамент экспертной разметки:

  1. определить и зафиксировать JSON-схему;
  2. написать загрузчик и строгую валидацию;
  3. объединить expert + wavelet так, чтобы экспертная разметка всегда имела приоритет;
  4. не считать неразмеченную область отрицательной;
  5. принудительно добавлять экспертные события в обучающие кандидаты;
  6. сохранять источник каждой метки: expert или wavelet;
  7. считать отдельный proposal recall относительно экспертных событий;
  8. добавить тесты и обновить оба документа.

  Второй блок — локальный интерфейс разметки поверх уже готового формата.

  Так мы сначала проверим правильность самой логики на 38811 и 38818, а затем построим UI, который будет сохранять
  данные в уже устойчивом формате. Это будет существенно надёжнее, чем сразу привязать обучение к конкретной реализации
  интерфейса.
